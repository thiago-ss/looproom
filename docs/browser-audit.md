# Coordinator browser baseline recipe

Status: implemented and tested against a read-only snapshot of actual project records. The actual baseline remains unavailable: the selected snapshot has no pending human Review gate. Fixture tests verify report arithmetic and cannot establish a browser baseline. Native judge activation is tracked separately in the workspace wiki.

`runBrowserBaseline` is a fixed coordinator capability. It receives an assigned task worktree, the coordinator's data directory and selected project/database identity. It never grants the worker a browser, live database, account files or new shell commands. The snapshot module captures one selected project in a bounded SQLite read transaction, strips account material and raw run output, hashes the private snapshot, and serves a separate loopback viewer. The viewer answers only the required read routes and rejects mutation methods. It does not start the engine or proxy live APIs.

The runner calls `runVerification` with the exact `npm run build` recipe. Only a successful unchanged-source isolated build can export a checked `dist` artifact. The runner records the task's Git HEAD and source fingerprint, exported build hash, snapshot ID/hash, browser and Playwright versions, Mac processor/memory/version, protocol hash and the SHA-256 of this evaluator module. A task commit is not substituted for the source fingerprint when the worktree has uncommitted changes.

Chrome launches under Playwright in a fresh private context with service workers and downloads disabled. Chrome uses the snapshot viewer as a fixed HTTP proxy, with implicit loopback bypass removed and no DIRECT fallback. Foreign HTTP origins and CONNECT tunnels are refused without forwarding; WebSockets are closed. This preserves the warm-cache protocol: Playwright HTTP routing disables cache. The browser cannot contact the live coordinator through the viewer. The trusted runner stores reports under `browser-audit/<report-id>.json` and screenshots/trace/build under `browser-audit/<report-id>/`. These artifacts may contain project content and stay in the private data directory. A worker handoff should quote the report ID, source/snapshot/protocol identities and redacted findings, not copy raw screenshots or snapshot JSON into a PR.

Protocol version 1 uses the frozen Goal, Work, Review and Memory order at 1280×800 and 390×844. It records one warm-up and five fresh-tab samples at each viewport, with a shared browser context. Browser Performance API marks and observations supply activation-to-settled timings, navigation/resource bytes and long tasks. Keyboard checkpoints use native Tab, Shift+Tab, Enter, arrows and Escape. The runner bounds native traversal to two focus cycles to account for controls hidden after activation, compares the focused element with the intended control, and inspects its in-viewport rectangle and painted outline or shadow. Clipping against viewport and scroll/clip ancestors, dropped long-task entries, and resource buffer overflow are recorded. Style inspection and screenshots support review; they are not a screen reader announcement test. A pointer fallback after an unreachable keyboard target preserves a measurable workflow while recording the keyboard defect. Work and Memory selection choose a different record when one exists and wait for its selected state; search waits for matching results or response, and filter waits for the changed filter. A sole Review gate or Memory outcome is recorded as a focus/read path without claiming a selection transition. The raw samples determine p75 by nearest rank, median, and maximum observed long task. Screenshots and a Playwright trace retain failure context.

`validateBrowserReport` rejects a complete claim when source/build/snapshot/evaluator/browser identity is missing, the 30-minute budget is exceeded, a viewport lacks its warm-up/five samples, any required operation or keyboard checkpoint is absent, or aggregates differ from raw observations. A recorded focus failure, horizontal overflow or UI error can be a complete baseline finding; unknown focus or missing timing is unavailable. `compareBrowserReports` requires the same project/snapshot/evaluator/browser environment. It keeps a candidate only when its target p75 improves by at least 10% and 50 ms at both viewports, every other operation stays within 10%, and there is no new request/UI error, focus failure or horizontal overflow. Missing metrics return `unavailable`, never `keep`. This is a comparison utility; the engine does not call it to authorize candidate publication. A complete browser report means complete measurement, not a passing optimization. Automatic experiment promotion integration is a separate delivery.

The controlled snapshot measures real project records but not concurrent live coordinator behavior. An absent open Review gate, fewer than two Work tasks, missing cited Memory outcome, unavailable PR diff, failed Chrome launch, or unsupported PerformanceObserver produces explicit unavailable data. Such a report stays immutable and cannot be pinned as a complete baseline. No result in this document claims a measured speedup or accessible production UI.


## Installation and boundaries

Install locked dependencies with `npm ci` and install Google Chrome from its vendor. The recipe uses `playwright-core` 1.63.0 and `channel: "chrome"`; it does not download a browser or fall back to another engine. A missing/incompatible browser returns unavailable. Each report records the exact installed version and headless mode. This is a controlled copy of actual records, not a live user-session or screen-reader announcement test.

The project-scoped transient FTS5 index keeps matching/token/query semantics. If the original index includes several projects, its BM25 ranking can differ; `counts.indexedProjects` makes that caveat inspectable. Source capture includes counts of open gates and distinct cited sources. The viewer uses a per-run capability cookie, independent from the live app session. It holds no account credentials, runtime engine, approval API or live proxy.

Complete engine acceptance and subsequent pinned handoff reopen the report/snapshot and verify every regular trace/screenshot file's canonical reserved path and SHA-256. Reports are copied byte-for-byte by immutable ID to `.looproom-verification`; private artifact paths remain references, not worker access grants. Do not publish snapshots, browser traces or screenshots containing project content in public PRs. Browser reports do not overwrite configured-check `latest.json`. Fresh complete evidence clears exhausted judge retries; missing observations never satisfy the machine blocker. For a selected human PR gate, the coordinator freezes public PR details and the base-to-head diff using read-only GitHub CLI requests. Repository, PR number, open state, head SHA and base branch must match the selected project and gate. The base/head are rechecked after capture; failed or changed bindings remain unavailable. These details become part of the snapshot hash. The viewer serves only these frozen responses; it has no GitHub write or merge route.

Primary references: [Playwright context routing/cache](https://playwright.dev/docs/api/class-browsercontext#browser-context-route), [Chromium proxy configuration](https://chromium.googlesource.com/chromium/src.git/+/refs/heads/lkgr/net/docs/proxy.md), [SQLite snapshot isolation](https://www.sqlite.org/isolation.html).

The native keyboard route chooses the shorter Tab or Shift+Tab path based on current focus and visible tab stops, then verifies the actual focused element. Workstream/Connections and Library/Sources use roving tab focus: Tab reaches the selected tab, and ArrowRight selects and focuses its sibling. The measurement mark is placed immediately before that arrow.

For an actual PR gate, Review waits up to five seconds for the read-only PR revision and diff responses to render, and distinguishes a displayed load error from a timeout. The browser selects Full diff with the tab list's native arrow key and checks that the rendered diff is nonempty. When the reviewed revision is mergeable, native keyboard activation opens the merge confirmation; the runner records focus inside that dialog, presses Escape, and checks that focus returns to the opener. It never activates the confirmation button. A disabled opener or absent PR detail is recorded as unavailable rather than treated as a successful merge workflow.

The first actual-record audit exposed a measurement race: native Home was still scrolling when the Latest messages button appeared, so the former Goal scroll wait ended early and the following Enter could be overtaken by the remaining Home motion. The evaluator now ends `goal.scroll` only after the conversation viewport reaches the top and remains there across animation frames. This clarifies the existing activation-to-settled measurement; it does not relax the Latest messages success condition. Reports from the earlier evaluator remain immutable and unavailable for comparison.

A later actual-record snapshot exposed a second observer race in the Latest messages keyboard route. The rich conversation contains a focusable child before the Latest control; Tab into that child scrolls the conversation to the bottom, which can remove Latest before a separate per-key observer call returns. For this target, the evaluator computes the short native Tab route from the current DOM and sends those key presses consecutively, then checks the actual focused element. A detached or missing target is recorded as unreachable; no DOM focus or pointer activation is counted as native keyboard success. Earlier reports retain their original evaluator hash and results.

The Latest messages observation now requires a trusted Enter keydown while the visible button is actually focused and the conversation is still at its settled top, a trusted keyboard click on that button, and a settled bottom with the button hidden. Merely hiding the button when Tab scrolls a rich message into view is not activation. If the focus scroll removes the button before Enter, the runner records missing native activation and continues other views without assigning a timing to `goal.latest`. A prior evaluator counted some pointer recovery timings after this race; those immutable reports remain unavailable and must not be compared with the corrected evaluator.

PR diff capture uses a bounded child-process buffer just above the snapshot's 2,000,000-byte UTF-8 diff ceiling. A valid diff between one and two megabytes can be frozen; larger output is rejected. A read failure, changed binding, invalid response, or oversized diff omits only that gate's frozen PR detail. The actual project, tasks, messages, memory, and other valid PR details remain in the immutable snapshot. The viewer returns 404 for the missing gate detail, and the browser report labels that Review observation unavailable. Capture exceptions are not copied into the snapshot because they can contain private paths or credentials.
